# Market Intelligence Engine — Platform Architecture

**status:** implemented and tested (21 tests green) · **date:** 2026-07-08

The Market Intelligence Engine (MIE) is a **research software platform**, not a set of backtest
scripts. It is organised as a stack of layers, each with one job, wired together by a central
orchestrator. **Strategy Evaluation is one module inside the engine** — the same orchestration would
drive other research modules (a data-quality auditor, a portfolio constructor, a causal-inference
module) without change.

```
        ┌─────────────────────────── Market Intelligence Engine (app/) ───────────────────────────┐
        │                                                                                           │
        │   Research Core ──drives──▶ Strategy Evaluation ──emits──▶ Knowledge Base ──feeds──▶ Meta- │
        │   (orchestrator,            (one research module:          (the corpus:            learning│
        │    versioning,               providers→walk-forward→        dossiers, results,     (mines  │
        │    module registry)          stats→verdict)                 INDEX, meta ledger)    patterns)│
        │        │                                                          ▲                     │   │
        │        ├──────────────────────── AI Research Assistant ───────────┘  (grounded Q&A) ◀───┤   │
        │        │                                                                                 │   │
        │        └─ Strategy Discovery Engine ─generates hypotheses─▶ (back into Research Core) ───┘   │
        └───────────────────────────────────────────────────────────────────────────────────────────┘
```

The **Strategy Discovery Engine** closes the loop: it reads the corpus + meta-learning, composes new
hypotheses from indicator building blocks under learned priors, and feeds the most promising (frozen,
pre-registered, auditable) back into Research Core / Strategy Evaluation. Full design:
`docs/STRATEGY_DISCOVERY_ENGINE.md`.

## 2. Main modules (responsibilities)

- **Research Core** — the only layer that knows the *order of operations*. Resolves the frozen
  matrix version, asks the requested module to evaluate, hands the report to the Knowledge Base, and
  triggers meta-learning. Holds no science itself.
- **Strategy Evaluation** — the science of *one* research question: is a trading rule a real,
  robust edge? Providers → walk-forward OOS → cost/slippage stress → benchmarks → deflated-Sharpe /
  BH-FDR / bootstrap → mechanical verdict. Pluggable data and pluggable strategies behind interfaces.
- **Knowledge Base** — the corpus and the *only* way to read/write it. Enforces data integrity
  (synthetic never sets a verdict) and versioned persistence.
- **Meta-learning** — turns "we tested N strategies" into "here is what separates robust from
  fragile": verdict distribution, per-class behaviour, generalizers, meta-hypothesis tallies.
- **AI Research Assistant** — answers research questions using *only* recorded corpus facts, with
  citations. The deterministic retrieval seam an LLM front-end plugs into.
- **Strategy Discovery Engine** — the generative + learning layer. Composes hypotheses from
  indicator building blocks (never hand-coded), prioritises them with meta-learning priors, avoids
  repeatedly-failed traits, and feeds frozen/pre-registered/auditable candidates back into Research
  Core. Records generated strategies in a **separate** `G-####` namespace and tracks their survival
  across rounds — every proposal traceable to the versioned policy that produced it.

## 3. Data flow

```
real OHLCV (provider)                                   ← Strategy Evaluation / providers
  → EvalRequest(target, assets, matrix_version)         ← Research Core / orchestrator
  → module.evaluate() under the frozen matrix           ← Strategy Evaluation / evaluation
      walk-forward OOS → costs/slippage → benchmarks → stats → mechanical verdict
  → EvaluationReport                                    ← returned to the orchestrator
  → KnowledgeBase.record(report)                        ← Knowledge Base / store + dossier
      dossier STEP-5 (versioned) · INDEX row · results/<id>.<ver>.json · meta_ledger.json
  → meta_learning.mine(kb) → LEARNING_REPORT.md         ← Meta-learning
  → assistant.answer(q) reads KB.query                  ← AI Research Assistant (on demand)
```

Every hop is deterministic and reproducible from `(request hash, matrix hash, provider)`.

## 4. Command-line commands

One entry point, `python -m app.cli`:

```
mie list strategies|providers|matrices|modules      # what the engine can do
mie matrix                                           # frozen-matrix version log
mie evaluate --target H-010 --assets AAPL,BTC/USD --matrix v2      # run one strategy
mie batch    --targets H-003,H-004,H-006 --assets AAPL,SPY --matrix v2   # run many, then learn
mie learn                                            # re-mine the corpus → LEARNING_REPORT.md
mie discover --propose-only --k 5                    # generate + explain WHY (dry run, no test)
mie discover --k 4 --rounds 3 --assets AAPL,BTC/USD --matrix v2   # closed loop: generate→test→learn
mie ask "which strategies generalize across markets?"    # grounded assistant answer
mie kb show H-010                                    # a strategy's recorded result
```

`evaluate`/`batch` run the full Research-Core flow (evaluate → record → learn). The legacy
`python -m app.strategy_research.run …` still works for module-level runs; the CLI is the platform
surface. The same operations are exposed over HTTP by `app/routers/strategy_research.py`.

## 5. How results are saved

Three coordinated artifacts, all under `trading_research/knowledge_base/`:

- **Human dossier** `H-0xx_*.md` — the 7-step record. STEP 5 is written per matrix version: a v1 run
  fills `## STEP 5`, a v2 run adds `## STEP 5 · srp-matrix-v2` **without touching v1** (history is
  never overwritten).
- **Machine results** `results/<id>.<version>.json` (immutable archive per version) **plus**
  `results/<id>.json` (a "latest" pointer). Each record carries verdict, OOS Sharpe, deflated
  Sharpe, robustness/stability/generalization, drawdown, trade count, `matrix_version`, and the
  request+matrix hashes.
- **Catalogue & tallies** `INDEX.md` (verdict/scores per strategy, tagged with the matrix version),
  `meta_ledger.json` (meta-hypothesis votes), and the generated `LEARNING_REPORT.md`.

Data-integrity rule enforced at write and read: **synthetic (`is_real=False`) runs never set a
verdict in INDEX/meta and are excluded from meta-learning and assistant answers.**

## 6. How srp-matrix-v2 is versioned

The evaluation matrix (cost ladder, slippage ladder, walk-forward splits, benchmarks, thresholds,
pooling) is a **content-addressed, immutable object**. `research_core/versioning.py` is the registry:

| version | hash | pooling | role |
|---|---|---|---|
| `srp-matrix-v1` | `a740f3acbf6572d6` | concatenation | historical (first four strategies) |
| `srp-matrix-v2` | `4c2aa61eccfd276c` | per-asset-then-aggregate | **active** (all new work) |

v2 changes only the multi-asset drawdown pooling. The `version` string is the sole changed field, so
**v1's hash is provably unchanged**; `pooling` is a derived property (not hashed). Every result is
stamped with its matrix version + hash, so conclusions are never silently mixed across methods. A
future `v3` is added with `versioning.register_matrix(...)` — never by editing v1 or v2.

## 7. How new strategies are added later

Adding the remaining strategies — or any new one — touches **only the strategy module**, never the
engine:

1. Subclass `Strategy` (in `strategies/implementations*.py`): implement `positions(df, params)`
   returning `{-1,0,+1}` (causal — the backtester shifts it, so look-ahead is impossible) and
   `param_grid()` (its size is the data-snooping budget).
2. Register it (`register_strategy(cls)`, or add to the registry list).
3. Run it through the platform: `mie evaluate --target H-0xx --assets … --matrix v2`.

The orchestrator, Knowledge Base, meta-learning, and assistant pick it up automatically. All 23
built-in strategies are already implemented and pass the no-look-ahead check; only H-002/005/010/020
have been *evaluated* so far — the other 19 are ready to run inside this structure.

New **data providers** extend the same way (subclass `DataSource`, `register_provider`), and new
**research modules** register in `research_core/module_registry.py`.

## 8. How the AI assistant interacts with the Knowledge Base

The assistant is a **read-only, grounded** layer. `ResearchAssistant.answer(question)`:

1. classifies the question intent (a strategy id, generalization, the graveyard, "what works", a
   corpus summary);
2. fetches the relevant records **through the Knowledge Base query API** (`knowledge_base/query.py`)
   — never by reading files ad hoc, never by inventing numbers;
3. composes an answer from those records and returns it with `evidence` (the raw records) and
   `citations` (dossier / INDEX / results paths).

Because retrieval is deterministic and every fact is a recorded result, the answer is auditable. This
is exactly the seam a language-model front-end consumes: the LLM phrases the response, but the
**facts come from the corpus**, so the assistant is trustworthy rather than fluent-but-wrong. Synthetic
results are invisible to it by construction (§5).

## Design principles (why it's a platform, not scripts)

- **One flow, many modules.** Research Core owns the scientific method; modules own the science.
- **The corpus is the product.** Every run compounds into a versioned, queryable knowledge base.
- **Immutability & provenance.** Matrices and per-version results are never edited; history is kept.
- **Honesty by construction.** Synthetic can't become evidence; verdicts are mechanical; look-ahead
  is structurally impossible; the assistant can only speak from recorded facts.
